# Verification and acceptance testing of releases

## Rules

Select tests based on the effects of the change. The most important are seating rules, authorization, time, ranking and durability. Use PostgreSQL for transaction testing; SQLite and repository mocks do not validate locks. The clock and the source of randomness must be controllable in tests. Report commands and results from the actual run, and explicitly mark checks that were not run.

## ELO properties (K=32 approved, remaining rules according to D8)

For identical pre-match ELO averages: 5:0 gives +16/−16 per person; 3:2 gives +3.2/−3.2; 3:3 gives 0/0. These examples constitute the criteria for an accepted scale.

- Peer teams: 5:0 causes a larger absolute change than 3:2.
- The same proportion, the same lineups and the same points before: 3:2 and 6:4 give the same increase.
- A draw between equals does not change the points; a draw between the weaker and the stronger gives the weaker an increase.
- Each member of the same team has equal delta, including the seventh rotator.
- Expected points use pre-match status; writing side A does not change the input for side B.
- Absent without ELO entry. Re-saving the same revision without another change.
- Recalculating the full history gives the same result as recording subsequent meetings and their approved corrections.

## Minimum E2E paths

1. Invitation → registration → declaration for a later date → refresh → status preserved → reopening with a session.
2. Participant resigns → manual creation of the proposal → waitlist player accepts → current list on the second device.
3. The administrator approves attendance → divides teams → corrects full lineups → approves → creates a list → saves the result → players see the ranking.
4. Date change → old confirmation invalid → re-confirmation; canceling the next date remains in the calendar without penalties.
5. Player tries other player's admin endpoints and history → refusal without revealing data.

Run the scenarios on a test seeder with a clear zone and time. UI check includes actual renders and screenshots; checking the generated HTML itself does not replace attempts in the browser.

## First release conditions

- The agreed scope of D9 runs from registration to the end of the match; no open rule implemented by accident.
- Backend lint/tests, frontend lint/typecheck/tests/build and required E2E completed successfully.
- Seat allocation concurrency, authorization and ELO property tests have supporting evidence; no known bugs affecting limit, privacy or point integrity.
- UI of variant A checked on the phone; no demo elements, secrets or test accounts in production.
- Target Home Assistant installation and non-LAN access checked; architecture and browser with the result in the report, not as a presumption.
- Backup and restore actually performed; given copy location, frequency and instructions for reproducing it without revealing secrets.
- Instructions for installation, updates, rollback and basic administrator actions are ready.

## Acceptance testing report

The report includes version/commit, environment and CPU, browser versions, tested scenarios with result, links to evidence, restore performed, open bugs and user's release decision. “The build passes” does not replace a report of actual application behavior.

Precision: the match series is calculated without intermediate rounding to 1 place; points and deltas in UI have 1 decimal place. Replaying the history gives the same state within a given tolerance. The UI format does not change the calculations.
