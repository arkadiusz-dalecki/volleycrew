# Domain, data and API

## Meeting settlements

- Store costs and shares in whole grosz. A series supplies a default for each occurrence. An individual price can be set to zero or reset to the default. A series edit updates inherited prices on future occurrences. Changes to price alone increase the data version and preserve the term version, declarations and offers.
- Confirming actual attendance posts the shares in the same transaction as attendance. Allocate leftover grosz in player ID order so the shares add up to the meeting cost. Confirming attendance for a meeting with no cost or a cost of zero creates no charge. A canceled or unattended meeting has no charge. Existing meetings and series migrate with a zero cost.
- A payment report selects outstanding meeting charges and includes the amount the player saw. Serialize settlement writes per player. Validate the selection and amount again on the server. A report may be pending, paid or rejected. The administrator can record an already received payment, confirm a report or reject it with a reason. A repeated command cannot post a new payment or alter a finalized review.
- Corrections recalculate the shares, record the differences and preserve the original payments. Confirmed overpayments offset the oldest outstanding charges first. Pending transfers retain their submitted amounts until review. Reminders use the remaining payable balance after credits and pending transfers, with strict thresholds of PLN 100 and 30 days from the oldest unpaid charge.
- Players can read their own balances and payments. The organizer's BLIK number or Revolut link appears to players with an amount due. The administrative dashboard and profile payment settings are restricted to administrators. Payment details do not appear in the ordinary player, roster or ranking responses.

## Common rules

- One group. Meeting limit: 14 participants. Administrator and priority status are independent properties. The priority status is not visible to other players: your own status is available in the profile, the administrator can see everyone's status. Own view remains the current assumption; the new instruction excludes public markings.
- Default schedule: Tuesday, 18:00–20:00, I LO in Gdańsk, `Europe/Warsaw`. The day of the week is a setting, not a limitation of the model.
- Store event dates as zone-aware UTC moments. The repeat rule includes the local time and IANA zone. Calculate the next date in the rule zone, not by adding 168 UTC hours.
- The limit for cancellation and protection of places is exactly 24 hours before a specific start. `now < starts_at - 24h` means the earlier period, `now >= starts_at - 24h` means the protected period. A regular withdrawal exactly at the boundary is not late; it becomes late only after the boundary. The server clock is the source of truth, injected in tests.
- „Nie będę”, waitlist, waiting for reconfirmation and refusal of offer do not constitute absence without cancellation.
- Enrollment and actual attendance are separate states. Only those actually present can enter the official lineups and ELO. The preliminary court from the declaration is a separate preview with no effects on attendance and ranking.

## Meeting states

Cycle play: `scheduled → attendance_checked → teams_confirmed → completed`. `cancelled` is a separate termination. Changing an appointment creates a new version of the appointment and a status requiring reconfirmation; does not create a new meeting ID. Rollback of approved lineups and corrections of a completed match are separate audit operations dependent on D5/D8.

The cancellation leaves the meeting in the calendar, closes the acceptance of declarations/offers and does not generate a no-show. The cancellation of a completed match should not be treated as an ordinary cancellation of a future date.

## Calendar and schedule

The calendar must extend as far into the future as you want, but it does not create an infinite number of records. The API presents calculated rule instances and existing encounters. Signing up for the calculated date resolves it to a permanent Meeting in the transaction. A range request can be limited in size and pagination, never restricted to “only the next week”.

Instance resolution verifies on the server side that the key matches a valid schedule or an existing exception. The player does not create any match by submitting his own date; declarations concern future, uncancelled meeting occurrences.

Rescheduling from a date preserves history. You need to handle both existing future enrollments records and instances that have not yet been generated. Before approval, the administrator sees a preview of the affected meeting occurrences. The change does not leave hidden, old meeting occurrences or duplicates. After rescheduling, we maintain the original order of enrollments (registration time and tie-breaking sequence). Confirmation of participation must be for the new version of the date; response time does not establish a new order. Approved 2026-11-06 (D4). The current space is reserved for responses, with no automatic deadline for responding. The administrator manually decides to free up space if there is no confirmation. A new application does not take up such a reservation. Approved 2026-11-06. Each subsequent change of the date requires confirmation of the current version of the date, maintaining the original order and seat reservations. This also applies to people with open offers from the waitlist: acceptance of the old offer is rejected, and acceptance of the place requires a new acceptance of the current date. Previous offers and confirmations remain invalid in the history; the same person's reservation is continued and not counted a second time. The organizer still manually transmits information on Messenger. Approved 2026-11-06 (D4). Test the effective date limit and day of the week change.

## Enrollments and places

Three priority statuses, from highest: founder (`founder`), player (`player`), guest (`guest`). A new profile always receives guest status; the status is changed by the administrator. Earlier than 24 hours before the start, this hierarchy decides, and within the status the order „będę”. A later enrollment may move the last lower-priority participant to the waitlist: a founder can displace a player or guest, and a player can displace a guest. The guest does not displace the player or founder. Approved 2026-11-06; replaces the earlier two-tier model. Once you enter the protected period, existing places are not taken away due to priority. Vacant seats may still be filled.

Changing the status by the administrator earlier than 24 hours before the start recalculates the priority while maintaining the time of the original registration. Changing your status in the last 24 hours does not deprive anyone of their seat. The recalculation respects offer reservations approved in D2 and does not reset the order of submissions. The operation is transactional and auditable. Approved 2026-11-06 (D3).

Resignation frees up space. If there is a waitlist, the seat is reserved for the first person in the queue; a new entry cannot take it over, even before the organizer has sent the proposal. The organizer manually contacts via Messenger and decides when to forward the proposal to the next person. In the first version there is no automatic response timeout. Moving from the waitlist requires acceptance of the offer; do not automatically transform a waitlisted player into a participant. The model distinguishes between allocated seat, pre-proposal reservation and active offer; the transfer cannot create two reservations for the same seat. The sum of assignments, reservations for waitlists/offers and places waiting for reconfirmation after rescheduling cannot exceed 14; the same place is counted only once. Approved 2026-11-06. After a refusal or manual termination of the proposal due to lack of response, the person's application for a given date is withdrawn, without marking an absence or late resignation. May report again, with a new reporting time and sequence; status still determines the priority level. If there are several available places, reservations are given to different people from the waitlist, each for one place; one person cannot receive two parallel reservations. Approved 2026-11-06 (D2).

### Enrollment mutation transaction

1. Read and lock the Meeting row (`SELECT FOR UPDATE`). All operations competing for space use the same lock.
2. Check permissions, meeting status, profile lock, appointment version and clock.
3. Save the declaration/offer and calculate allocations according to the approved policy.
4. Save history events and meeting version, commit everything together.
5. Return the current state of your own declaration, list and waitlist. Repeating the same operation does not change the order or create another history entry.

Acceptance of the offer verifies the identity of the recipient, the validity of the offer, the version of the date and the availability of the reservation. The old screen cannot accept the revoked offer. Changing the term invalidates references to the previous version; user gets conflict and new state.

## Withdrawals and attendance

Regular resignation, late resignation and absence without cancellation are distinguished in private history. No automatic penalties.

Exception: accepting an offer from the waitlist in the last 24 hours allows you to later cancel without the late cancellation label. Eligibility results from the server event of accepting an offer; a regular late enrollment does not qualify for this exception. The exception does not cover absences without notice.

A no-show is created after the administrator explicitly confirms attendance, not just after the start time has passed. A candidate is a person with a confirmed seat who has not withdrawn and has been marked as absent. Commit retry does not create duplicates. Canceled meetings are always excluded. The administrator can correct incorrect attendance marking by providing a mandatory reason. The original entry remains in history; correction indicates the author, time, and source event, and the current state includes the correction. Both the original entry and the correction with the reason are available only to the administrator and the given player. Approved 2026-11-06 (D5). The administrator marks the late person as present, without a separate penalty for being late. When an absence has been previously approved, the correction uses the corrections mechanism with the reason. The administrator can add a person without prior declaration only from an existing, unblocked profile, if there is a free, unreserved place and the total limit of 14 is not exceeded. The operation does not skip reservations and is audited. The justification is recorded as a correction with the reason, retaining the source event; is not an automatic history deletion. Approved 2026-11-06 (D5). Correction history does not secretly change approved lineups, score or ELO; their corrections are subject to separate operations and D8.

## Teams and ELO

The draw for official teams is based on those actually present. Balanced mode minimizes the difference in ELO averages with a cardinality difference of at most 1 and at most 7 per side. With 14 people, you can deterministically review the combinations with A/B symmetry removed. Establish an explicit tie-break in the code. Admin can change lineups; each person exactly once, no one absent can be added with a hidden UI change.

The court diagram shows six people and a possible seventh for rotation. We do not record playing time, positions or changes in sets. The entire approved lineup receives a rank change.

Assumptions confirmed: start 1000, team strength as the average of points before the match, one update after the match, result in sets. Proportion of sets instead of number of sets played; a draw with a stronger team can increase points.

K scale = 32 approved on 2026-11-06 (D8). For equal teams, each player receives: 5:0 → +16/−16; 3:2 → +3.2/−3.2; 3:3 → 0/0. Rating changes for unequal teams take their strength into account.

Implementation pattern D8: K=32, expectation scale 400 and precision policy approved on 2026-11-06/07:

```text
EA = 1 / (1 + 10 ** ((meanB - meanA) / 400))
SA = setsA / (setsA + setsB)
K = 32
deltaA = K * (SA - EA)
deltaB = -deltaA
```

Everyone in A gets deltaA, everyone in B gets deltaB. In case of unequal numbers, do not force the sum of all players' points to zero at the expense of changing the rule of equal deltas in the team. K is 32. We keep exact values in calculations and permanent records, without rounding points after each match; UI shows points and deltas to one decimal place. Averages and expectations use computational, not presentational, values. Approved 2026-11-06. Set the numerical representation and comparison tolerance in E8. Expectation scale 400 approved 2026-11-07.

The result 0:0 closes the match with the mark „bez rozegranych setów”, without ELO update and without division by zero. Attendance remains recorded; do not equate such closure with the cancellation of a meeting. Approved 2026-11-06. The Meeting model distinguishes between a played match and a completion without sets. Save the played result atomically with RatingEntry, active revision and match status. Retry does not update the ranking a second time.

Admin can correct the result with mandatory reason. The previous result remains in the history along with the author and time corrections. After correction, recalculate the ranking also for later matches, as their pre-match ratings have changed. Approved 2026-11-06 (D8). The conversion uses a stable order of fixtures and their approved snapshot lineups. The operation blocks concurrent result writes; the ranking and change log are published atomically, without showing half the conversion. Correction from 0-0 to a score played or vice versa also requires consistent recalculation. 2026-11-07 full corrections of historical attendance and lineups with reason and order by start time and permanent meeting ID have been approved.

## Access and sessions

Registration via a permanent, random, reusable link, without administrator approval. The new profile has guest status (`guest`) and no administrative privileges. The server assigns this status regardless of the fields sent by the client; registration does not allow you to choose a higher priority yourself. The invitation can be rescinded; an existing user does not need a login link.

Login is a separate, unique name of 3-32 ASCII characters (letters, numbers, dot, dash, underscore), normalized to lowercase letters and without leading or trailing spaces. Password is 8-128 characters long, preserves all spaces and Unicode without normalization/truncation; Argon2id with salt. No character set enforcement. The change replaces the old profile and PIN selection (decision 2026-11-15); public directory `/auth/profiles` and old PIN operations are removed. Login in DTO only for your own account and administration list, without logins in group/print lists.

After 5 incorrect account passwords/15 minutes, we reject subsequent attempts until the end of the window (HTTP 429, Retry-After); separately 30 errors/source/15 minutes. Unknown login also passes Argon2id and the same counters/error. The case of the letters does not allow you to bypass the limit of your existing account. Counters remain in PostgreSQL. Registration/bootstrap/reset maintain a limit of 10 operations/source/15 minutes. The reset is granted by the organizer with a one-time link valid for 30 minutes, without automatic sending. Allows you to choose a login and password; Login collision does not consume token.

Random session in HttpOnly/Secure/SameSite=Lax cookie, in DB only hash. 30 days of inactivity, maximum 180 days; renewal up to the hard expiry limit. Mutations require CSRF and Origin, Ingress/domain inputs have separate cookies. Changing/resetting the password invalidates sessions and pending reset grants and creates a fresh session for the current device. Changing your password yourself keeps Google; a reset from the organizer removes its association.

A lock invalidates sessions, blocks all logins, releases future slots/reservations, closes offers, and preserves history/ELO. Status and place changes respect transactions D2–D6. The nickname is still changed by the player himself; it is used to distinguish names and is not a login.

Migration 0012 removes old PINs, invalidates sessions and grants, preserves profiles. The user does not require player migration (only the organizer's account). The new operator grant setup allows the administrator profile without a password to set new data while retaining ID, role and history. The old token used is not renewed; after setting password bootstrap closed. No simple PIN login or automatic creation of a second organizer.

## Details of E3 implementation

`ScheduleVersion` has a local date range of `[effective_from, effective_until)` and a weekday number from 0 (Monday) to 6 (Sunday). PostgreSQL excludes interval overlap. The default rule has been in effect since 1970-01-01; this does not create an encounter history. Past meeting occurrences in the calendar come only from persisted records, without creating an apparent history from the rule itself.

The instance ID is UUIDv5 from the schedule version and source date. The meeting retains these fields and ID after changing the actual start. GET the calendar doesn't create anything; merging also suppresses the original date when the rescheduled appointment falls outside the requested month. `POST /meetings/resolve` takes `{schedule_version_id, source_date}` and idempotently persists the correct future or ongoing date. Does not record participation; it does not create a completed instance, but it also returns an existing record historically. E4 declarations must independently validate the future start, cancellation and term version.

`/calendar` range is semi-open (`from` inclusive, `to` exclusive), Europe/Warsaw dates, from 1 to 366 days on request; pagination `limit/offset`, response `items/total/next_offset`. Public in the sense of a group does not mean anonymous access.

The duration is the actual number of minutes from the start in UTC. The generator rejects a non-existent or ambiguous local start time (e.g. Sunday 02:30 on the day of the time change); the Tuesday 18:00 rule is clear. ## Details of the implementation of E5

User approved 2026-11-06: shifting the permanent rule in the same week Monday-Sunday, keeping cancellations and individual exceptions without shifting. Preview marks exceptions separately. The new rule replaces the scheduled rules from the specified date; superseded versions remain as superseded, without removing the associated history. A conflict, collision, or offset before the beginning of the scope blocks the commit instead of merging the data.

The meeting retains the ID and original source. `calendar_schedule_id/calendar_source_date` identify the new rule slot that is currently being replaced, so that the same term does not appear twice virtually. Resolver recognizes both keys. The preview is recounted on save and compared with a token including the meeting/rule versions and the requested change. The ScheduleState lock coordinates materialization, calendar reading, and bulk mutations.

With each actual change, term_version increases. Previous dates and the persistent MeetingTermRevision retain a trace of the change. All going requests require a new confirmation: existing places go to reserved/reconfirmation, the waitlist retains the order, active old offers are invalidated and new protected reservations in the current version of the date are given. Confirmation does not reset declared_at or queue_number; acceptance of the offer still requires a new proposal and acceptance of the current date. No timeout, manual release by the administrator. Each subsequent change repeats this process.

Canceling a future meeting preserves declarations and history, resets allocations, closes active offers and leaves cancelled in the calendar. It generates neither a no-show nor a late dropout. Ended or started meetings are not affected by this operation. The source of the new confirmation is always the current term_version, not the old application or the old offer ID.

Non-existent/ambiguous DST times are discarded at setup, without unreconciled shifting in the background. The bulk change also checks for collisions with calculated slots that have not yet been created. Detailed contract, limits and proofs: [E5 report](e5-report.md).

The current classification follows the latest correction by sequence. Correction actual attendance updates `Attendance`, seat allocation and attendance revision. If a team draft exists, it is archived and requires a new split. In the case of approved lineups, they must first be explicitly reopened; once the result is recorded, physical attendance is closed to rules E8. Simply changing the classification of an absence to an excused one does not change the lineup.

`TeamSheet` is a versioned draft/committed lineup/archive, with attendance revision affected. `TeamMember` stores one player's membership including lineup, side, presentation order and snapshot points. The order of presentation does not indicate actual position or playing time. There is at most one active lineup; We do not overwrite the archived file. Correction draft passes full A/B lists and must include everyone present exactly once. At 7:7, a two-person exchange is performed, without temporarily registering the eighth person in the team.

The random generator uses the system's source of randomness (injected in tests). The balanced generator examines combinations, minimizes the absolute mean difference, removes symmetry in equal numbers, and breaks the tie lexicographically by player ID. In E6 everyone has an actual starting rating of 1000; downloading converted rankings will be connected in E8. The seventh person is presented in rotation. Public for the logged in group, the reading returns only the approved lineup, never draft or private history.

E6 endpoints (prefix `/api/v1`):

- `GET/PUT /admin/meetings/{id}/attendance`, `POST .../attendance/confirm` - read, write, draft and commit.
- `POST .../attendance/admit`, `POST .../attendance/release-reservation`, `POST .../attendance/corrections` - venue and corrections support.
- `GET /me/attendance-history` and `GET /admin/players/{id}/attendance-history` - private history with pagination after source entries (`limit` 1–50, `offset` ≥0), with corrections and authors.
- `GET /admin/meetings/{id}/teams`, `POST .../teams/generate`, `PUT .../teams`, `POST .../teams/confirm`, `POST .../teams/reopen` - lineups support.
- `GET /meetings/{id}/teams` - approved teams or `null`, available to logged in players.

Each E6 mutation requires administrator, CSRF, `expected_version` meeting and UUID in `Idempotency-Key`. One Meeting row lock includes attendance, seats, history, lineup and operation confirmation. Retry of an identical operation with the same key returns the current state without retrying. Another payload under the same key or an old version for a new operation gives 409. Attendance records/lineups and their publication are atomic. E6 migration moves previously classified EnrollmentEvent opt-outs to a private history without changing the source dates and authors.

## Signature List - E7 implementation

`GET /api/v1/admin/meetings/{id}/signature-list` returns `application/pdf`. Default `Content-Disposition: inline`; optional `?download=true` sets `attachment` and the name `lista-podpisow-YYYY-MM-DD.pdf`, with the date of the meeting in its zone. Reading requires a session and a real admin role. The absence or deletion of an object gives a 404, a cancellation gives a 409. Before confirming the presence, we print the confirmed places; the waitlist is not exported.

Once attendance is confirmed, the source is records `Attendance.confirmed_state=present`, also for a historical profile locked after the meeting. Previously, the source is active confirmed places `Enrollment` for the current version of the term. One Meeting block, shared with corrections and admissions, allows you to download a consistent revision of the presence and its name. The lock is then released and the PDF is created in the thread pool from the immutable snapshot. The reading does not change attendance, version of the match, teams or ranking. Each new request retrieves the current state. The `X-Attendance-Revision` header identifies the document revision, and `Cache-Control: no-store` excludes the HTTP cache.

The PDF contains the date and time of the local meeting, the I LO in Gdańsk, the number of people on the list and the table: No., name and surname, signature. Order by surname, first name and ID, without revealing the ID on the printout. Does not contain nicknames, statuses, points or history/corrections. Blank signature spaces are intended for handwritten signatures; it is not an electronic signature form.

A4 format, Noto Sans font embedded in the file, line spacing of at least 14 mm. The usual list of 14 people, also with long Polish surnames, fits on one page. For extreme, multi-line names allowed by the profile limit, the table advances to the next A4 page, repeats the heading, and does not truncate names or lines. No presence gives an explicit message and zero items. OFL licensed fonts come with a backend; generation does not connect to an external website and does not create a permanent document archive.

## Results and ranking - E8

The `elo-sets-v1` algorithm uses K=32, expectation scale 400, starting rating of 1000 and set ratio. All calculations, averages and delta addition run on Decimal in a local context of 50 significant digits. PostgreSQL Numeric notation does not impose a decimal scale; we do not quantify the result to its post-match presentation value. Power and division have a finite computational precision of 50 digits; we do not declare symbolic/arbitrarily infinite accuracy. Identical replay produces identical saved values; tests compare them exactly, and comparisons to independently rounded benchmarks allow a tolerance of 1e-40. Public JSON uses decimal strings, frontend shows points and deltas to one place.

The order is `(Meeting.starts_at, Meeting.id)`, ascending. Adding an older result and each correction recalculates the history in the same order. Team splits use current converted points; the saved lineup is a snapshot of the membership and is not re-randomized during replay. Each participant of the side receives the same delta, including the seventh rotating one. Different page sizes do not force a zero sum for the entire group. For example, with equal averages, 5:0 gives ±16, 3:2 and 6:4 give ±3.2, 3:3 gives 0. With 1000 versus 1200, the weaker players receive +8.3 for a draw; stronger players lose 5.1 if they win 3:2.

`ResultRevision` stores an immutable set version, author, time, algorithm, and TeamSheet version reference. The previous version remains in the database, and at most one per meeting is active. `RatingState` versions the published ranking and is blocked before recording the Meeting. `RatingEntry` (pre/delta/post points), `RatingCalculation` (average/expect/proportion/deltas) and `PlayerRating` are materializations of the current replay from immutable inputs, exchanged atomically in the same transaction. Changing the revision does not add points to the current state a second time.

The result requires approved current lineups. Sets are non-negative integers; bool and fractions are rejected. The technical range corresponds to a positive PostgreSQL integer. 0:0 closes the match against `state=no_sets`, preserves attendance and lineups, does not create a RatingEntry or increase the number of ranked matches. In the performance history it remains visible. Changing to/from 0:0 also recalculates later matches. A draw with sets played is a ranking match, even if the delta is zero.

The pre-save preview shows the actual entry points for the match's place in the history, expectations and deltas, not simply the current points of all players. The record requires expected_version of the meeting, expected_rating_version from the preview and Idempotency-Key. A new save with an old preview gives 409. Identical retry of the same key returns the current state without new revision/points; other payload under this key is rejected. The RatingState shared lock protects rating, score and log readings from mixing parts of different conversions. Failure rolls back all changes, including score, attendance, lineup and receipt.

Full historical correction has a separate preview and approval. Requires a general reason and complete A/B lists. Any person added to or removed from the actual attendance requires an explicit, separate attendance change with a private reason. The one added receives `present`, the one removed receives `no_show` or `excused`; You cannot remove someone from the points by hidden changes to the lineup itself. Every actual attendee belongs to exactly one lineup: 2-14, max. 7 per side and the difference in size is 1 at most. Existing historical profiles are allowed, also blocked at the moment; correction does not restore their access to the application.

Correction creates a new committed TeamSheet and ResultRevision, updates Attendance and its private events, then publishes the result and full recalculation together. For a previously unregistered participant, a source attendance entry is created with the reason for the addition; other corrections point to an existing entry. We do not rewrite past declarations and reservations: this is the source history of enrollments, and the historical correction reflects the actual match. The number of participants of the completed meeting and the PDF are taken from the current Attendance, not from the old Enrollment. The waitlist of a completed meeting is not an active list to be added at the venue.

The group sees points, match history, current pre/delta/post changes and previous versions of the result with author/time. He does not receive reasons for corrections or private attendance events. The administrator additionally reads the reasons and previous lineups; the player still sees his own private attendance correction. Locked profiles retain points and history; ranking does not publish block, role or priority status flags. Everyone, even without ranked matches, starts from 1000. The position is calculated from unrounded points; identical values share a position, and the presentation is ordered by surname, first name and ID.

E8 endpoints, prefix `/api/v1`:

- POST `/admin/meetings/{id}/result-preview`, POST `/admin/meetings/{id}/result` - preview and first save.
- POST `/admin/meetings/{id}/result-correction-preview`, POST `/admin/meetings/{id}/result/corrections` - full correction with reason and optional presence changes.
- GET `/admin/meetings/{id}/result` - result, personal reasons and previous lineups for the organizer.
- GET `/meetings/{id}/result` - result and versions without private reasons; null before first save.
- GET `/ranking`, GET `/results`, GET `/players/{id}/rating-history` - ranking, match history and currently converted points history. Limit 1–100 and offset≥0; your own and other people's point history are group, attendance history remains private.

## Supplement: deleting meetings, editing series and printing before the meeting (2026-11-08)

The administrator can delete a future unstarted or canceled meeting. Deleted appointment does not appear in calendar/next, opens via old URL/API, or recreates when resolving the instance. In the database we keep an invisible instance tag (`deleted_at`), identity and audit; we close places/offers without marking absences. The history of matches played/supported is protected. Deleting a canceled appointment is also available after its date. Changing the schedule moves the deletion markers to the new rule so that it doesn't accidentally restore them.

There is a schedule version and a preview token that contains versions of all affected meetings. ## Entry protection - supplement E2, 2026-11-14

Before parsing the body and accessing the DB, `POST /auth/login`, `/auth/register`, `/auth/bootstrap` and `/auth/reset-pin` undergo an additional request burst limiter: 10 requests in a short burst per source, renewal 30/min; common process budget 20 requests, renewal 4/s. The common budget also includes traffic from many sources. The rejection gives the standard error `rate_limited`, HTTP 429 and `Retry-After` in seconds. The limiter runs in single process memory (like the current Uvicorn configuration), with a maximum of 1024 sources; restart/eviction does not clear persistent PIN or operation counters in PostgreSQL. It does not replace proxy protection against volumetric attacks. The ingress prefix and source address are subject to legacy trust rules.

Log `volleycrew.security` records the result of the input operation: success, invalid data, inactive link, CSRF error, and persistent limit or burst limit. Contains only UTC time, constant event type, operation name and HMAC fingerprint of the source with the instance key; no raw IP, profile ID, names, path/query, body, PIN, tokens or cookies. Maximum 60 events per minute/process, then one `security_logs_suppressed` marker; further events are skipped to a new window. This is limited operational telemetry, not a full audit of all attempts. The existing audit of account changes remains in the DB.

## Google - Supplement E2, 2026-11-15

Optional Google is an additional way to log in to an existing profile. Registration still requires an invitation and password. `GoogleIdentity` stores `player_id` (PK/FK), a unique verified `sub` and the connection date. No matching by email/name, no creating accounts from callback, no role/status assigned from a token. Google's scope is `openid` only; We do not store access/refresh/ID tokens or email. One Google account has one profile and vice versa.

`POST /auth/google/start` adopts `{mode: login|link, password?, return_to?}`. The link requires an active session and fresh password verification according to existing permanent limits. The returned URL leads to Google with PKCE S256, nonce and state. `GoogleFlow` only contains state/browser/nonce hashes, internal return target, optional connecting session, dates and consumption. The PKCE verifier is created from the HMAC of the instance key and state; we don't save it in the DB. The browser-binding cookie is `__Host-vc_google_flow` (Secure, HttpOnly, SameSite=Lax, Path=/; local HTTP uses the developer name). TTL 10 minutes; a new flow of the same browser replaces the previous one. Expired records are deleted on the next start.

`GET /auth/google/callback` is an external OAuth callback, protected by one-time state and cookie instead of POST CSRF. State is consumed transactionally before code exchange, without holding a DB connection/auth lock during I/O. Google RS256 signature and JWKS key, issuer, audience, exp/iat, azp and nonce are verified with the JWT library and OIDC checks. Reuse/different browser/expiration are rejected. The binding rechecks the exact same active session and profile activity after the code exchange. Identity conflicts are serialized by existing auth lock and DB restrictions. Login creates a regular Volleycrew session after the current ID and profile lock reading. The return target must be an internal route, with no fragment, schema, host, control characters, backslash, or API route.

`GET /auth/google/config` only returns `{enabled, public_url}`. `GET /me/google` returns its own `{connected}`. `POST /me/google/disconnect` requires `{password}`; unbinds, invalidates sessions and pending binds, issues a fresh session on the current device. Administrative password reset also removes the Google association to close the door to a foreign connection. It's up to Google to change your password yourself. Connection/disconnect/login is audited without external token data.

Google start has a persistent limit of 60 operations/source/15 minutes, shared with a given group instance, to also support a shared proxy address. It covers the existing short series POST gateway. Callback has a separate budget for short bursts with the same parameters (10/source, renewal 30/min; 20/process, renewal 4/s) so that starting logins does not consume the return budget. A rejected callback returns to a clean `/login#google=limited` with Retry-After; does not leave code in the JSON error screen. Other password/reset/registration limits remain unchanged. Google Telemetry has the same protection against secrets and log flooding.

Google Flow only runs under the main `PUBLIC_URL`. Ingress does not start or end its own OAuth; UI opens the main domain in a new tab. We do not transfer HA sessions and permissions. The change requires `0011_google_login` migration and new optional OAuth client configuration data.
