# Volleycrew building plan

Date: 2026-11-06. Status: plan to be implemented in stages; some rules require decisions. The documents do not mean the beginning of implementation or deployment.

## Purpose and boundaries

Private application of one volleyball group, with Arkadiusz as the initial sole administrator. Users sign up for meetings, the organizer handles attendance, teams, results and signature list. ELO is fun. UI: accepted variant A, clear, comfortable on the phone.

The first release is intended to cover the full cycle from invitation, through declarations and match, to history and ranking. The order of feature delivery is in the backlog; previous demonstrations do not mean production readiness.

Outside the scope of the first release: payments, automatic penalties, Messenger integration and automatic messaging, push notifications, point statistics, rotation tracking, multiple groups, native applications and automatic HA account permissions. Installing the site on the phone screen is desirable; Offline enrollments are not required.

## How to use the plan

1. Read [architecture](architecture.md) and [decision register](decisions.md).
2. Select a ready task from [implementation stages](tasks.md); check dependencies and blocking decisions.
3. Backend and database: read [domain and API](domain-api.md). Frontend: [interface specification](frontend.md).
4. Apply the appropriate [verification and release criteria](verification.md) before completing the task.
5. Record the result in the progress table below. The next agent should be able to reproduce the state based on documentation, code, and test results.

The documents describe the target behavior. E1 already provides a frontend, API and migration framework in `volleycrew/`; E2 adds access and profiles. E3 adds a schedule, calendar and persistent meeting occurrences. E4 adds declarations, priorities and a waitlist with offers. E5 adds previews and schedule changes, postponements, cancellations and reconfirmations. E6 adds actual presence, private history with corrections and versioned teams on the Variant A court. E7 adds a locally generated PDF of the signature list with authorized preview and download. E8 adds scores, ELO ranking, point history and full historical corrections with atomic conversion. E9 integrates UI, accessibility and network/session resiliency; acceptance testing on physical phones and visual comparison remains open. E10 provides HA suite and local tests for both CPU, Ingress and recovery; User self-installation and release are subject to acceptance testing. `prototype/` is a separate visual reference. Verification status and restrictions: [E1 report](e1-report.md).

## Decision hierarchy

User commands take precedence. Confirmed product rules are recorded in `domain-api.md` and `frontend.md`. The proposed solutions are marked with identifiers D in `decisions.md`. When a decision changes specifications, update the relevant document; the register is intended to keep the date and justification, not a copy of the entire rule.

The technical architecture is the foundation of the plan based on a previous proposal. Specific dependency versions and publication details should be verified in E0. The agent should not treat values from the prototype, sample ports, or open ranking parameters as requirements; scale K=32 is already approved in domain-api.md.
